# SalmonFlow

A frontend allocation workspace for 5,200 customer orders. It loads initial data through a Mock Service Worker API, automatically allocates after loading, supports manual adjustments, and keeps warehouse stock and shared customer credit consistent. Built directly in this repository, without a nested project folder.

## Run locally

Use Node.js 22.12+ (22.x) or 24.x. This project was verified with Node.js 24.18.0.

```sh
npm install
npm run dev
npm run build
```

Open the local URL printed by Vite. No credentials, backend, or database are required.

## Stack and structure

React and TypeScript provide the interface and explicit data types. Vite handles development and production builds. Tailwind CSS handles styling. The local shadcn/ui-style Button uses Radix Slot and class-variance-authority. TanStack Table supplies filtering, sorting and pagination. decimal.js provides precise prices and credit calculations. Vitest covers business rules; Lucide supplies icons.

- `src/types.ts`: order, inventory, customer and allocation models.
- `src/data.ts`: deterministic customers, inventory and 5,200 orders.
- `src/allocation.ts`: pricing, ordering, eligibility, automatic and manual allocation.
- `src/App.tsx`: initial API loading, error handling, retry and request cancellation on unmount.
- `src/api.ts`: fetches the initial dataset and rejects unsuccessful HTTP responses.
- `src/mocks/handlers.ts`: the shared MSW GET handler returning deterministic mock data with a 500ms delay.
- `src/mocks/browser.ts`: starts browser request interception once and supports retry if startup fails.
- `public/mockServiceWorker.js`: the worker script generated by the MSW CLI; do not edit it manually.
- `src/components/AllocationWorkspace.tsx`: shared allocation state, derived dashboard data, Auto/Manual actions and component composition after data loads.
- `src/components/AppLayout.tsx`: sidebar, header, content area and footer. Receives the active tab and navigation callback.
- `src/components/DashboardSummary.tsx`: the four dashboard metric cards, using values calculated by AllocationWorkspace.
- `src/components/InventoryTable.tsx`: remaining inventory by warehouse, supplier and item.
- `src/components/AllocationSummary.tsx`: allocation status counts, reasons for incomplete orders and a callback to filter the order table.
- `src/components/OrderTable.tsx`: search, filters, date sorting and 25-row pagination.
- `src/components/AllocationPanel.tsx`: accessible dialog, source selection and validation.
- `src/components/ui/button.tsx`: shared button with shadcn/ui conventions.
- `tests/allocation.test.ts`: preserved business logic tests, run only when explicitly requested.
- `tests/navigation.test.tsx`: preserved UI/API integration tests, run only when explicitly requested.

## Initial data loading

The app starts MSW before making `GET /api/allocation-data`. The handler returns a JSON object containing `orders`, `customers` and `inventory` from `data.ts`. The loading screen stays visible while the worker starts and the request is pending. A failed request shows an error and Retry; Retry repeats the load. An AbortController cancels requests when the loading component unmounts, including React Strict Mode's development cleanup, and stale results are ignored.

Once data loads successfully, AllocationWorkspace mounts and runs automatic allocation with the received dataset. It is not necessary to click Run auto allocation. The existing allocation algorithm remains independent of fetching. After loading, Auto and Manual change React state only; there are no allocation write endpoints or background refetches to overwrite manual edits.

This is a frontend-only demo: MSW stays enabled in both development and the production build so the built demo also works without a backend. Tests use MSW's Node integration with the same handlers, not a browser service worker. For a real backend, remove the browser mock startup and provide the same response contract at the API URL. Browser service workers require HTTPS or a localhost development origin. Follow the [official browser integration guide](https://mswjs.io/docs/integrations/browser). Regenerate the worker after updating MSW using `npx msw init public --save`.

## Allocation algorithm

1. Copy inventory, customers and existing allocations so original data stays unchanged.
2. Sort orders: Emergency, Overdue, Daily; oldest date first; order ID breaks ties.
3. Subtract previous allocations from the requested quantity.
4. Find positive stock for the item matching the warehouse and supplier restrictions. `WH-000` allows any warehouse and `SP-000` allows any supplier. Sort eligible inventory records by remaining quantity descending, with stock ID breaking ties.
5. Calculate the selected source's adjusted unit price, rounded to two decimals with half-even (Banker's) rounding.
6. Allocate the minimum of outstanding request, stock and affordable whole units. Update stock and the customer's shared credit before processing the next source or order.
7. Record source, quantity, unit price and cost. Re-running allocation processes only outstanding quantities and cannot double count existing allocations.

The inventory scan is small (12 records). Automatic allocation uses maps for shared credit and existing quantities. The UI renders only 25 table rows, avoiding thousands of DOM rows. Filtering remains client-side over the 5,200 records.

## Business assumptions

- Quantity is measured in whole units, not fractional kilograms. Negative, fractional and zero manual additions are rejected.
- Currency is THB. Emergency is 125%, Overdue 100%, Daily 90% of the supplier's base price, following the example.
- Each item/warehouse/supplier inventory record has a base price. Prices do not vary over time; no tax or delivery fee is added.
- The unit price is rounded first, then multiplied by whole units. Credit is stored as decimal strings and money arithmetic uses Decimal. Half-even examples: 1.005 becomes 1.00; 1.015 becomes 1.02.
- Credit is a remaining spending allowance shared across all of a customer's orders, not a per-order limit.
- Highest remaining stock means the eligible item/warehouse/supplier record, rather than aggregate stock across unrelated records.
- Overdue is supplied explicitly as an order type; dates are not used to reclassify priorities.
- Every generated row represents one allocatable sub-order with a unique order ID. A parent-order grouping is not specified and is not introduced.
- IDs, dates and mock data are deterministic. Dates are UTC date-only values. Item IDs correspond to the examples; all sources have valid positive prices and customers. Adjusted unit prices must remain finite and greater than zero after rounding; invalid prices raise an error before allocation rather than treating the stock as free.
- A pending order has zero allocation; partial means some but less than requested; allocated means the full request. The dashboard's pending count includes both partial and unallocated orders.
- Incomplete order reasons describe current constraints: no eligible stock, or credit insufficient for any eligible unit. Stock restriction is reported first if no source remains.

## Manual allocation

Select an order using its ID or row arrow. The drawer shows its request, current allocation, remaining request, source restrictions, actual allocated sources with quantities/prices/costs, and the reason it is complete or incomplete.

Manual editing replaces the selected order's total allocation. Existing sources are prefilled; change their quantities or eligible warehouse/supplier, add sources, or remove sources. Zero releases a source's quantity; removing all sources releases the entire allocation. Quantities must be non-negative whole units. Other orders are untouched.

`releaseOrderAllocation` creates a temporary state with this order's quantities returned to inventory and its recorded costs refunded to customer credit. `replaceOrderAllocation` validates each positive draft entry using the same stock, credit, request and pricing rules as automatic allocation. React commits the new state only after every entry succeeds. Invalid edits and Cancel leave the saved state unchanged. The displayed editing credit and source stock include this temporary refund; current credit and allocation details show saved values. New costs use the chosen source's current adjusted unit price.

Auto retains priority/FIFO rules. Manual is an explicit operator adjustment, not a guarantee of FIFO across orders; editing existing allocations is a documented workflow assumption beyond the assignment's basic manual-add requirement. Manual cannot take stock or credit reserved by another order. Re-running Auto preserves saved allocations and may refill quantities released by a manual edit. The drawer supports Escape, focus trapping and focus restoration.

Summary cards open the order table with the corresponding status filter. Auto completion messages report additional units and orders, or explain that no further allocation is possible. Incomplete orders can also become actionable after a manual release; the summary reports these separately.

## Tests

Tests are kept separately in `tests/` for later study and are not part of the application source or the production TypeScript check. Neither `npm run dev` nor `npm run build` runs them. The standard `npm test` script has been removed; when you choose to use them again, explicitly run `npm run test:manual`. Vitest and jsdom remain installed so the preserved tests can still be used.

The preserved tests check priority, FIFO, deterministic tie-breaking, source eligibility, each wildcard, supplier prices, type adjustments, half-even rounding, stock and credit shortages, shared credit, partial allocation, invalid manual additions, repeated allocation, input immutability and conservation of stock/credit over 5,200 orders. The dataset test prints the allocation duration without imposing a machine-dependent performance threshold.

## Limitations and deployment

Demo state lives in React and resets on refresh. No persistence, authentication, import, order cancellation or credit top-up is included. Releasing an allocation does not delete its order. A customer without eligible stock or credit may still be unable to receive additional units; editing can only reuse this order's existing resources and unallocated resources. Browser performance depends on the device. There is no backend or concurrent-user synchronization.

Build output is `dist/`. Deploy to Vercel as a Vite project with build command `npm run build` and output directory `dist`. This delivery is local; no deployment URL or remote GitHub repository has been created.
